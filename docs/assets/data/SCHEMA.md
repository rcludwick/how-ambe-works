# Precomputed data — schema and provenance

Everything the site's animations draw is precomputed and stored here as JSON.
The animation code loads these files and renders them; it performs no AMBE
analysis or synthesis, and this repository contains no AMBE codec.

Generated by `tools/make-data.py` from the hardware capture that
`tools/make-audio.sh` and `tools/capture-hardware.sh` produce. Regenerating is
a three-step chain:

```
tools/make-audio.sh        # Piper -> 8 kHz mono WAV originals
tools/capture-hardware.sh  # originals -> real AMBE-3000 -> frames + decoded WAV
tools/make-data.py         # audio + frames -> the JSON described here
```

**Provenance of the current build: 2026-08-11.** The clip behind every file
here is `lr-b`, `"CQ CQ CQ this is a test of the AMBE voice codec."`, spoken by
the Piper voice `en_US-libritts_r-medium` (speaker index 690, LibriTTS-R
speaker 240, CC BY 4.0), synthesised at 22050 Hz and resampled to 8 kHz, then
round-tripped through a DVSI AMBE-3000. The full recipe, model checksums,
speaker choice and corpus licences are in `docs/assets/audio/MANIFEST.md`.
Sustained device throughput, which sets what a bigger capture would cost, is in
`probe-rate.md` next to this file.

## Provenance: two kinds of number, never mixed

Every value in these files is one of exactly two things, and the files are
structured so you can always tell which:

**MEASURED** — bytes that came off a DVSI AMBE-3000 chip. In practice this is
one thing only: the 72-bit channel frame per 20 ms, in `frames.json` as
`frames[].hex`. Everything else the chip told us is device metadata (product
ID, version string).

**DERIVED** — ordinary DSP computed from the two WAV files by
`tools/make-data.py`: frame RMS, a tracked autocorrelation pitch estimate, FFT
magnitude spectra, band-limited voicing strength. These describe the *audio*.
They are not codec state. In `frames.json` they live under a `derived` key on
every frame; in `spectra.json` and `waveform.json` the whole file is derived
and says so in its `provenance` / `decoded_alignment` fields.

!!! warning "What is deliberately absent"

    The AMBE-3000's packet interface carries speech samples in one direction
    and channel bits in the other. **It has no packet that reports the codec's
    internal parameters.** The fundamental-frequency index, the per-band
    voicing bits, the gain index and the spectral-amplitude indices therefore
    cannot be observed from outside the chip, and no field in these files
    claims to be them. Nothing here was inferred by taking the frame apart.

    Where the site needs a pitch contour or a voiced/unvoiced picture, it uses
    the derived measurements below. Those are measured on the *decoded* audio —
    the chip's own output — so they track what the codec decided closely, but
    they remain measurements of a waveform, not the transported bits.

## Hardware that produced the capture

| Field | Value |
| --- | --- |
| Device | NW Digital Radio ThumbDV |
| Chip | DVSI AMBE-3000 |
| `PRODID` | `AMBE3000F` |
| `VERSTRING` | `V121.E100.XXXX.C110.G514.R014.A0030608.C0020208` |
| Interface | USB serial, 460800 baud, DVSI AMBE-3000 packet protocol |
| Mode | D-STAR full rate: 2400 bit/s voice + 1200 bit/s FEC = 72 bits per 20 ms |

The same block appears as the `hardware` object in `frames.json` and
`clips.json`. Encode and decode were run frame-at-a-time in lock step: one
20 ms speech frame in, one 72-bit channel frame out, and then those frames
back in the other direction, on the same physical device.

## Files and layout

```
docs/assets/data/
  SCHEMA.md          this document
  clips.json         index of all eight clips
  probe-rate.md      measured device throughput, and the method
  frames.json    \
  waveform.json   >  the featured clip (lr-b), also present in lr-b/
  spectra.json   /
  <clip-id>/         the same three files for each of the eight clips
    frames.json
    waveform.json
    spectra.json
  frames/
    <clip-id>.ambe   raw hardware output: concatenated 9-byte channel frames
```

Clip ids are `<voice>-<sentence>`, voice ∈ {`lr` (male,
`en_US-libritts_r-medium`), `lj` (female, `en_US-ljspeech-high`)}, sentence ∈
{`a`, `b`, `c`, `d`}. The featured clip is `lr-b`; load
`assets/data/frames.json` for it, or `assets/data/lj-c/frames.json` for
another.

All internal paths (`original_audio`, `decoded_audio`, `channel_frames`) are
**site-root-relative**, matching `anim-core.js`'s `assetURL()` / `loadJSON()`
convention. Pass them straight to `loadJSON()` or `assetURL()`.

Every file carries a `schema` string (`how-ambe-works/<kind>/<version>`) and a
`generated_utc` timestamp. If a field you rely on is missing, check `schema`
first.

## Units and conventions used throughout

| Convention | Value |
| --- | --- |
| Sample rate | 8000 Hz, mono, 16-bit signed |
| Frame | 20 ms = 160 samples = 72 channel bits = 9 bytes |
| Full scale | 32768 (so `dBFS = 20·log10(amplitude / 32768)`) |
| dB floor | −100 dBFS; values are clamped, never `-Infinity` |
| Time | seconds, from the start of the *original* audio file |
| Frequency | Hz |
| Booleans | real JSON `true` / `false` |

### The `voice` object

The same object appears in `clips.json` and in the `clip` block of all three
per-clip files.

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | `lr` or `lj`, the clip-id prefix |
| `sex` | string | `male` or `female`. For `lr` this is a measurement of pitch, not a corpus fact: see `docs/assets/audio/MANIFEST.md` §1 |
| `model` | string | the Piper voice, e.g. `Piper en_US-libritts_r-medium` |
| `speaker` | string | which speaker of a multi-speaker model was used |
| `dataset` | string | the training corpus, with a URL |
| `dataset_license` | string | that corpus's licence |
| `attribution` | string or `null` | the credit line a reuser must carry; `null` when the corpus is public domain |

`speaker`, `dataset`, `dataset_license` and `attribution` are metadata about how
the audio was made. Nothing in the animation code reads them; they are there so
that a file taken out of this repository still says where its speech came from.

### The delay field, and why you need it

The decoded WAV is *not* sample-aligned with the original: the chip's encode
and decode pipelines each add latency, and measured end to end it is 253–275
samples (31.6–34.4 ms, i.e. between one and two frames) on these clips. Delay
was measured by cross-correlating the 20 ms RMS envelopes of the two files and
taking the peak; the correlation at that peak (0.967–0.991) is also the
cleanest single number for "the decoded audio really is the same speech".

`waveform.json` has this shift already applied to its decoded track, and
`frames.json` / `spectra.json` apply it when analysing decoded audio. If you
play the two WAVs against a shared clock, apply it yourself.

## `frames.json` — the channel frames, per 20 ms

| Field | Type | Meaning |
| --- | --- | --- |
| `schema` | string | `how-ambe-works/frames/1` |
| `generated_utc` | string | ISO 8601 UTC build time |
| `clip` | object | clip block (below) |
| `hardware` | object | the hardware table above |
| `measured` | object | prose describing what `frames[].hex` is |
| `unavailable` | string | prose stating which codec fields are not observable and why |
| `derived_notes` | object | `method`, `bands`, `band_edges_hz` |
| `frames` | array | one object per 20 ms frame, in order |

`derived_notes.band_edges_hz` is an array of `[low_hz, high_hz]` pairs, eight
equal 500 Hz bands covering 0–4000 Hz. It indexes `band_voicing` and
`band_voiced`.

### `frames[]`

| Field | Type | Units | Provenance | Meaning |
| --- | --- | --- | --- | --- |
| `i` | number | — | — | frame index, 0-based, contiguous |
| `t` | number | s | — | start time of the frame in the original audio: `i × 0.02` |
| `hex` | string | — | **MEASURED** | the 72 bits the AMBE-3000 emitted for this frame: 18 lowercase hex characters = 9 bytes, first byte on the wire first, MSB first within each byte. This is the FEC-protected D-STAR channel frame as transmitted, not the underlying 48 voice bits. |
| `derived` | object | — | DERIVED | see below |

Bit order, spelled out, because animations that draw individual bits depend on
it: `hex[0:2]` is byte 0, and bit 0 of the frame is the most significant bit of
byte 0. Bit *n* (0-based, 0 ≤ *n* < 72) is
`(bytes[n >> 3] >> (7 - (n & 7))) & 1`.

The site does not decompose the frame further, because the mapping from these
72 bits to codec parameters is not something the device will tell us.

### `frames[].derived` — DSP measurements, not codec fields

| Field | Type | Units | Meaning |
| --- | --- | --- | --- |
| `orig_rms_dbfs` | number | dBFS | RMS of the original audio over this frame's 160 samples |
| `decoded_rms_dbfs` | number | dBFS | RMS of the decoded audio over the same 160 samples, after the delay shift |
| `orig_f0_hz` | number | Hz | tracked fundamental of the original; `0.0` when the tracker calls the frame unvoiced |
| `orig_f0_confidence` | number | 0–1 | normalised autocorrelation at the chosen lag; `0.0` when unvoiced |
| `decoded_f0_hz` | number | Hz | same estimator on the decoded audio; `0.0` when unvoiced |
| `decoded_f0_confidence` | number | 0–1 | as above |
| `voiced` | boolean | — | `decoded_f0_confidence ≥ 0.35` |
| `band_voicing` | array[8] | 0–1 | per-band voicing strength of the decoded audio, low band first |
| `band_voiced` | array[8] | — | `band_voicing[b] ≥ 0.55` |

How each derived value is computed, exactly:

- **Pitch.** A rectangular (unwindowed) 512-sample (64 ms) segment centred on
  the frame, mean removed, centre-clipped at 30 % of peak; normalised
  autocorrelation over lags
  20–160 samples (400 Hz down to 50 Hz). Per-frame peak-picking flips octaves,
  so candidates are the local maxima above 0.25 and the winner is chosen by a
  Viterbi pass over the whole clip that charges 0.55 per octave of frame-to-
  frame jump plus 0.20 to enter or leave an unvoiced state, with unvoiced
  costed at `1 − 0.35`. The chosen lag is refined by parabolic interpolation.
  On this set the original and decoded tracks agree to a median 0.6–1.1 % and a
  90th percentile of 1.4–4.3 %.
- **Voicing, whole frame.** Simply `decoded_f0_confidence ≥ 0.35`. The
  threshold was chosen by eye against the audio; it is a display convenience,
  not a specification.
- **Voicing, per band.** The same 64 ms window of decoded audio is split into
  eight 500 Hz bands with an FFT band-pass (zero every bin outside the band,
  inverse transform), and each band's normalised autocorrelation is evaluated
  at the frame's pitch lag. A band carrying harmonics of the fundamental
  repeats at that lag and scores near 1; a band carrying noise does not and
  scores near 0. `0.0` for every band when the frame has no pitch estimate.
  This is the classic band-pass voicing-strength measure applied to ordinary
  PCM — it is *not* the codec's voicing decision.

## `waveform.json` — scrubbable envelope

Min/max pairs, not raw PCM. One bucket is 20 samples (2.5 ms), and there are
exactly 8 buckets per 20 ms frame, so `frame = bucket >> 3` and
`bucket = frame × 8`.

| Field | Type | Units | Meaning |
| --- | --- | --- | --- |
| `schema` | string | — | `how-ambe-works/waveform/1` |
| `generated_utc` | string | — | ISO 8601 UTC build time |
| `clip` | object | — | the clip block described above |
| `bucket_samples` | number | samples | 20 |
| `bucket_ms` | number | ms | 2.5 |
| `buckets_per_frame` | number | — | 8 |
| `bucket_count` | number | — | `frame_count × 8`; the length of every array below |
| `sample_full_scale` | number | — | 32768 |
| `decoded_alignment` | string | — | states that the decoded track is already delay-compensated |
| `original.min` | array[int] | sample units | most negative sample in each bucket of the original |
| `original.max` | array[int] | sample units | most positive sample in each bucket of the original |
| `decoded.min` | array[int] | sample units | same for the decoded audio, delay-compensated |
| `decoded.max` | array[int] | sample units | same |
| `closeup_samples` | number | samples | 480, the length of each closeup below |
| `closeup_note` | string | — | prose saying why the closeups exist |
| `closeups` | object | — | two windows of raw samples; see below |

Values are integers in [−32768, 32767]. Divide by `sample_full_scale` for
−1…+1. All four arrays are exactly `bucket_count` long; a bucket past the end
of the audio is `0`.

Bucket *k* covers original-audio time `[k × 0.0025, (k+1) × 0.0025)` seconds in
both tracks — the decoded track was shifted earlier by
`clip.decoded_delay_samples` before bucketing, so a scrub cursor lands on the
same phoneme in both. Derived by FFT-free min/max reduction of the WAV files.

### `closeups` — raw samples, for showing periodicity

The buckets above are 2.5 ms, about a third of a pitch period. They can draw
a whole sentence and they cannot show that voiced speech repeats. These two
windows are the actual 8 kHz samples of the **original** audio, so that a
figure can show the pulse train itself.

| Key | Meaning |
| --- | --- |
| `voiced` | the loudest 60 ms window the pitch tracker is confident about: a vowel |
| `unvoiced` | the loudest window it is not confident about: a fricative |

Each is an object:

| Field | Type | Units | Provenance | Meaning |
| --- | --- | --- | --- | --- |
| `frame` | number | — | — | index of the 20 ms frame the window is centred on |
| `start_s` | number | s | — | window start, from the start of the original audio |
| `f0_hz` | number or `null` | Hz | derived | tracked pitch, or `null` when the tracker is below `VOICED_CONF` and reports none. Never `0` |
| `f0_confidence` | number | 0–1 | derived | normalised autocorrelation at that period |
| `rms_dbfs` | number | dBFS | derived | level of **this 480-sample window**, not of the 20 ms frame that selected it |
| `samples` | array[int] | sample units | measured from the WAV | exactly `closeup_samples` values |

Both windows are chosen by `closeups()` in `tools/make-data.py` from the
per-frame measurements, not by hand, so they follow the audio if a clip is
ever recaptured. A sentence with no loud fricative still gets an `unvoiced`
window; it will simply be quiet. `lr-d` is the example, at −62 dBFS.

## `spectra.json` — per-frame magnitude spectrum

| Field | Type | Units | Meaning |
| --- | --- | --- | --- |
| `schema` | string | — | `how-ambe-works/spectra/1` |
| `generated_utc` | string | — | ISO 8601 UTC build time |
| `clip` | object | — | the clip block described above |
| `bins` | number | — | 128 |
| `fft_size` | number | — | 256 |
| `window` | string | — | `Hann, 256 samples (32 ms), centred on the frame` |
| `bin_hz` | number | Hz | 31.25 — width of one bin |
| `bin_centre_hz` | array[128] | Hz | centre frequency of each bin: `k × 31.25`, 0 … 3968.75 |
| `units` | string | — | `dBFS, integer, floor -100` |
| `floor_db` | number | dB | −100 |
| `provenance` | string | — | states that this is FFT of the audio, not codec output |
| `original` | array[frames][128] | dBFS | spectrum of the original audio, one row per frame |
| `decoded` | array[frames][128] | dBFS | spectrum of the decoded audio, one row per frame, delay-compensated |

Rows are in frame order and align 1:1 with `frames[]` in `frames.json`: row *i*
is the 32 ms Hann window centred on the middle of frame *i*. Values are
**integers**, rounded dBFS, clamped at −100; expect roughly −100 to −10 on this
material. The window's coherent gain is compensated, so a full-scale sine would
read 0 dBFS at its bin.

Bin 0 is DC. Bin 127 is 3968.75 Hz. There is no bin at exactly 4000 Hz: the
256-point real FFT's Nyquist bin is dropped so that every row is exactly 128
values.

Derived by `numpy.fft.rfft` of the audio files. Nothing about the codec's
internal spectral representation is claimed by these numbers — they are the
spectrum of what came out of the loudspeaker, on both sides.

## Audio files these reference

`docs/assets/audio/` holds sixteen WAVs, 8 kHz mono 16-bit:

- `<clip-id>-original.wav` — Piper text-to-speech, resampled to 8 kHz.
- `<clip-id>-ambe.wav` — the same audio after a round trip through the real
  AMBE-3000 hardware.

`docs/assets/audio/MANIFEST.md` is the authority on how they were made: voice
models and their checksums, the speaker chosen from the 904 in the male model,
synthesis parameters, the exact resample command, and the corpus licence for
each voice. The male clips carry a CC BY 4.0 attribution requirement.

**Normalisation.** Every WAV, original and decoded alike, was scaled by a
single constant gain so its RMS lands on −20 dBFS, backed off if that would
push its peak above −1 dBFS. No compression, limiting, EQ or noise reduction
was applied to any file. The gains applied to the decoded files were small
(−0.66 to +0.03 dB) because the codec preserved level well; the point of the
step is that an A/B comparison hears timbre, not loudness.

The originals were additionally trimmed of leading and trailing silence and
padded with 80 ms of lead-in and 120 ms of tail before encoding, so that the
encoder has a frame or two to settle.
